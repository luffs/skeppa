# Skeppa — self-hosted deploy panel

Deploys private GitHub repos onto this server via webhooks, manages encrypted ENV vars, runs apps with pm2 (or in containers, or publishes them as static sites). Single user. No Docker for the apps; deploy scripts can optionally run in a rootless-podman build sandbox.

## Technology choices (decided — do not change without discussion)

- **Runtime:** Bun. **Plain ES6 JavaScript — no TypeScript.**
- **Backend:** Hono on `Bun.serve` (WebSocket via `createBunWebSocket`).
- **Database:** SQLite via `bun:sqlite`, file `data/skeppa.db`. Migrations are numbered `.sql` files in `server/src/db/migrations/` run by the homemade runner in `migrate.js`.
- **Frontend:** Vue 3 SFCs with the **Options API — not Composition API, no `<script setup>`**. Vite for tooling, vue-router. No state library.
- **Real-time:** live state and deploy logs travel as **lazy-storage stores** (lazy-watch diffs on the wire) over one WebSocket at `/live` — the browsers' only socket (the other, `/agent`, is for Fleet agents, below). The server keeps a LiveState proxy (`server/src/live/state.js`) that the poller, the runner and the routes write; nothing writes the stores directly — a bridge (`live/stores.js`) forwards each lazy-watch batch into read-only stores (`readOnly: true`) with `store.patch`: `panel` (system/users/images; admins), `fleet-<ownerId>` (that owner's projects and piers; the owner or an admin), `harbor` (proxy; anyone signed in). Isolation is store layout, because lazy-storage has no per-user read filter inside a store: `authorize` decides who may open one and every session on it sees every patch; fleets follow the crew list (a deleted user's store closes on their sockets). `live/transport.js` mounts `/live` (`createHandlers`, session-cookie `authenticate`, the HTTP snapshot route under it), ahead of the Hono app in index.js. The client (`web/src/live.js`) opens `harbor` + its own fleet (tenants) or `panel` + `harbor` + a fleet per user in `panel.users` (admins), mirrors each store into a Vue-reactive object with `LazyWatch.patch`, and composes `store.live` — `projects` and `groups` merged across fleets, the rest from `panel`/`harbor` — so views read the shape they always did; `store.ready` flips once every opened store is online, `store.connected` follows the socket. Deploy log lines are NOT in LiveState: a running deployment is its own store, `deploy-<id>` (`{ lines: { <zero-padded seq>: line } }`), opened, appended and closed by the runner's LogCollector through `liveStores.openLog/appendLog/closeLog`; opening it delivers the backlog as the snapshot, and the store is evicted when the deploy finishes, after which the client (`subscribeLogs` in `web/src/live.js`, same socket) reads the stored log from the API. Who may open one is `canReadDeployment`, wired in index.js (admins, or the project's owner — deploy logs echo ENV values). `bun scripts/live-mirror.js <url> <user> <password> [store ...] [--once]` follows the stores from a terminal. **Rules for LiveState writers.** `null` is not a value, it means "key removed" (a deletion to the stores; the boot seed drops nulls for the same reason): anything that reaches LiveState after boot must encode "unknown" some other way — `''` for strings (`getProxyInfo`), a companion flag for tri-state (`live/images.js` keeps definitions and engine facts apart, with `storeListed`, and joins them in the client), and for numbers just let the key vanish; client code using `?.`/`??`/`== null` cannot tell that from an explicit null anyway. `false` is not a substitute: it is falsy but not nullish, so `?.` throws on it (`commitSha?.slice(0, 7)`) and `== null` guards miss it (`bytes()` would print `0 kB` instead of `—`). **Shapes.** A store is collections of records and singletons, declared identically on both sides (`STORE_SHAPES` in server `live/stores.js`, `SHAPES` in `web/src/live.js`; `web/test/liveshape.test.js` holds the two to each other, and the server suite pins the values) — a client whose top level differs is answered `shape-mismatch` and never sees the store. `users`, `projects` and a fleet's `groups` are collections: records keyed by id, added and deleted on their own, so a record is a JSON **object** and every path inside it merges by itself. `system`, `images`, `proxy` and a deploy log's `lines` are one record each — `lines` necessarily, its values being strings. An array is a leaf written whole whatever it holds, so nothing has to be declared for one; the bridge substitutes the whole live array wherever lazy-watch emitted a fragment (`$length`, `$splice`, bare indices), so how LiveState edits an array does not reach the wire — `splice`/`unshift` on the proxy are still the cheap route for anything long. A server patch is the authority: it is stamped now and applied without checks, so a record recreated under a deleted key lands — LiveState does that constantly (containers after a deploy, pm2 entries, `headCommit`) — and nothing the bridge writes can be refused. lazy-watch value rules still apply to the proxy: assigning `undefined` is a deletion; `NaN`, `Infinity`, `Date`, `RegExp`, bigint, symbol and functions throw a TypeError on assignment — quantize first (`live/quantize.js` returns `null` for non-numbers) and keep instants as ms numbers or ISO strings. Both packages are workspace-pinned so server and client run the same versions.
- **Process management:** pm2 CLI (spawned, never a shell string) for the panel, the proxy and pm2-runtime apps. Per-project `projects.runtime` can be `container`: the app then runs in a rootless-podman container (`server/src/containers/runtime.js`) — source read-only at `/app`, `shared/` at `/data`, port published on localhost, crash restarts via engine restart policy, boot/env-refresh via panel recreation. The start command runs under `START_SHELL` (pid 1 passes SIGTERM on to it, and exits with its status), and a recreate stops the old container before removing it, so an app hears a stop or a deploy and gets its grace period instead of a SIGKILL. The panel itself must always be pm2 (enforced in routes), and its process is defined solely by the repo's own `ecosystem.config.cjs` — `writeEcosystem` refuses the self project (two specs for one pm2 name merge into a broken chimera on reload); self-deploys reload via the deployed checkout's copy of that file.
- **Host mounts:** `projects.mounts` (text, one `host:target[:ro]` per line, stored normalized; `''` = none) bind-mounts server directories — a network share mounted on the host — into a container app after `/app` and `/data` (`lib/mounts.js`, `mountBinds` in `containers/runtime.js`). Admin-only: a tenant's PATCH may send its mounts back unchanged, never different; POST with any is refused for tenants; a Crew move to a tenant refuses a project that has some. Host paths only under the config's `MOUNT_ROOTS` (`config.mountRoots`, sent to admins as `system.mountRoots`; empty = nothing mountable) and never at, around or under `config.mountGuarded` (DATA_DIR, APPS_DIR, the checkout, the config and master-key dirs); checked lexically on a change and again on realpaths before every create — a failure throws before the old container is stopped. Container targets `/`, `/app`(…), `/data`, `/proc`, `/sys`, `/dev` are refused; colons are not allowed in paths. Never in the build sandbox.
- **Static runtime:** `projects.runtime = 'static'` has no process, no container and no port. The deploy syncs and runs the deploy script as usual, then `deploy/publish.js` copies `work/<publish_dir>` (default `dist`; `''` = the working directory) into the panel-owned snapshot `APPS_DIR/<slug>/public` and swaps it in by rename; the harbor gate serves that snapshot. The snapshot is the security boundary — Caddy's file server follows symlinks and the working tree is tenant-controlled, so the copy takes regular files only, refuses a publish path that goes through a symlink, and skips dot-entries except `.well-known`; a failed build or copy leaves the previous site untouched. Status is `published` / `not published` (the poller checks the snapshot exists); start/stop/restart are refused (`deploy/control.js`), boot resurrection and the crash watch skip it, the UI hides the process controls, the Logbook tab, start command and port. Tenants may use `container` or `static` — never a host process. A missing publish directory fails the deploy with the built sites it did find (`findPublishCandidates`). Every publish carries the previous build's content-hashed assets (`HASHED_ASSET_PATTERN`, shared with the gate's caching rule) into the new snapshot for exactly one more deploy, tracked in `public.carried` next to the snapshot, so pages loaded before a deploy still find their lazy chunks.
- **Gate-served app files:** `projects.gate_files` on a container or pm2 app publishes `publish_dir` into the same snapshot (in `_deploy`, before the app is touched — a missing build fails there) and makes its gate route files-first: a `GET`/`HEAD` for a file in the snapshot (a directory path only via its `index.html`) is served by the gate, everything else is proxied to the port unchanged — no `encode` in front of the app. With no snapshot nothing matches and the route is a plain proxy, so the flag is applied to the gate on save; `_settle` keeps the snapshot while the flag is on and removes it otherwise. The files bypass the app's auth — the UI says so.
- **Configured vs deployed runtime:** `projects.runtime` is what the form says and what the next deploy will do; `projects.deployed_runtime` is what the last successful deploy did (`''` = never deployed). `liveRuntime(project)` in `lib/runtime.js` (`deployed_runtime || runtime`) is what everything acting on the running thing asks: the harbor gate's route kind, the poller's status, start/stop/restart, boot resurrection, the UI's process controls. Saving a runtime change therefore moves nothing; the deploy does, in `runner._settle`: the new thing is ready (published or started) → record `deployed_runtime` → reload the gate → only then remove what served before (old process/container, or the snapshot). A gate that refuses the new route on an app↔static switch undoes the record and fails the deploy with the old site still serving. **pm2 names are never trusted:** a project's `pm2_name` is an input only for pm2-runtime projects (otherwise derived from the project name and immutable), `skeppa-proxy` is refused and the panel's own name is only allowed for a pm2 project; a pm2 process is deleted only when `deployed_runtime` says the project really was one, and never when the name is reserved (`isReservedPm2Name`) — tenants choose project names, so a name alone must never reach `pm2 delete`.
- **GitHub:** GitHub App (JWT → installation token, cached). Not OAuth, not a PAT.
- **Auth:** username/password users (managed under Rigging → Crew) with roles: admins run the panel; tenants own, moor and deploy only their own projects, container-or-static runtime (never a host process) + podman-sandbox enforced server-side, convoy networks and subdomains namespaced by their handle (`subdomain.handle.base`) — or routed under a domain of their own (`users.domain`: `subdomain.<domain>`, `@` for the apex; tenant-only, unique, never under the base domain; a change re-applies the proxy and refreshes the owner's projects' live info), repo picker scoped to installations of their linked github_login. Removing someone who still owns projects goes through a move (Crew → Remove; `lib/reassign.js`, `GET|POST /api/users/:id/reassign`): the plan refuses what the new owner may not have (a tenant: no pm2 process — configured or deployed —, no host access, GitHub repos only from their own installation; anyone: a subdomain already routed in the new namespace, a root-of-domain site with nowhere to go) and lists what changes (addresses, convoy network names) before anything is written; the move re-applies the gate, and the stores bridge moves a project between fleets whole when its owner changes — the old owner stops seeing it at once. Ownership guards return 404, never 403, bcrypt password hash (`Bun.password`), session cookie. Optional Google sign-in via a Firebase web config (Rigging → Google sign-in): the frontend loads Firebase from the gstatic CDN (never the npm package), the backend validates ID tokens with the Identity Toolkit REST `accounts:lookup` and matches the verified Google email against `users.username`.
- **Panel config:** KEY=VALUE file at `SKEPPA_CONFIG` → `~/.skeppa/config` — a fixed path so the original checkout and self-deployed copies read the same values (dogfooding needs no Manifest config). The process env overrides the file per key; a repo `.env` is dev-only (Bun loads it into the process env, so it wins). A `master.key` next to the config file is the default `MASTER_KEY_FILE`.
- **Secrets:** AES-256-GCM with a 32-byte-hex master key, read from `MASTER_KEY_FILE` (chmod-600 file outside repo/DATA_DIR/APPS_DIR; loose perms warned at boot) with `MASTER_KEY` env as dev fallback; unique IV per value. Decrypted ENV lives only in memory: injected into the deploy script env and via the pm2 CLI's process env (`pm2EnvBase` in `lib/shell.js` + `appEnv` in `deploy/pm2.js`), never written into ecosystem files. On-disk `.env` is a per-project opt-in (`projects.write_env_file`). At boot the panel resurrects app processes itself (`deploy/resurrect.js`, honoring `projects.auto_start`: pm2 stop via the panel clears it, start/restart/deploy set it) — apps must never be `pm2 save`d (the dump stores env in plaintext).
- **Build sandbox:** with `SKEPPA_SANDBOX=podman`, deploy scripts run in throwaway rootless-podman containers (only `source/` mounted at `/work`) via the Docker-compatible REST API on the user unix socket (`server/src/containers/client.js`) — never by spawning a CLI, so ENV travels in request bodies in memory. Rootless Docker's socket is wire-compatible (`CONTAINER_SOCKET`). No fallback to host on engine errors — that would silently drop the sandbox. Default is `host` (legacy behavior).
- **Shipyard (managed images):** Containerfiles stored in the `images` table, built via the engine's `/build` with an in-memory tar context (`lib/tar.js`, homemade ustar — no deps) into the reserved namespace `localhost/skeppa/<name>:latest`. Missing managed images are rebuilt from the DB instead of pulled (`containers/images.js` `materializeImage`) — the engine store is cache, the DB is truth. Manual Shipyard builds pass `pull: true` (refresh FROM bases); self-heal rebuilds use cached bases. Registry images refresh via the Shipyard Pull button (`POST /api/images/pull`). Empty build context: no `COPY` of local files; no registry auth on pulls.
- **File viewer ("Freight" tab; the env editor next to it is the "Manifest" tab):** a read-only look into a project's `source/` checkout — `GET /api/projects/:id/files?path=` answers for folders and files alike (so a README's relative links can just be opened), `/files/raw` streams a download; there is no write route. The tree is untrusted (a tenant's repo, and their deploy script has it mounted writable): `server/src/lib/sourcefiles.js` whitelist-parses the path, resolves it with realpath inside the real root, then opens the file and — on Linux — checks where the open descriptor points (`/proc/self/fd`) before reading from that descriptor only; hence node:fs FileHandles there, not `Bun.file(path)`. `.git` is unreachable, and a file named exactly `.env` is refused (with `write_env_file` on it is the panel's plaintext copy of the Manifest). Markdown and syntax highlighting are homemade and escape-first (`web/src/lib/markdown.js`, `highlight.js`) because their output goes into `v-html` while an admin may be viewing a tenant's README: raw HTML is dropped, images are never loaded, links are http(s)/mailto or in-viewer `data-path` only.
- **Checkouts without the branch head:** `POST /api/projects/:id/clone` (`runner.clone`) runs only the deploy's `syncRepo` — no script, no ENV, no process, no deployments row — so the code can be read under Freight before anything is deployed; it holds the project's queue while git runs (a deploy asked for meanwhile waits; 409 while one runs), and LiveState `checkedOut` (a real boolean, read from disk at boot) tells the page to offer it. `POST /:id/deploy` with `{ sha }` redeploys an earlier commit, only one this project deployed successfully (`trigger = 'redeploy'`, `syncRepo({ sha })` resets to it, fetching it by id if a force-push removed it); `deployedSha` then trails the head, so the project reads as having new commits.
- **Slug rename (Rigging → Advanced → Slug, next to Scuttle):** `POST /api/projects/:id/slug` (`runner.renameSlug` → `deploy/rename.js`) holds the project's queue like a clone (409 mid-deploy) and moves everything named after the slug: what runs is taken down (container saved-logs → stop → remove; a pm2 process deleted, since a restart would keep its old cwd), `APPS_DIR/<slug>` renamed, the row changed, the ecosystem file rewritten, and only what was running is brought back under the new name; a restricted project's own convoy network goes with the old name; the route reloads the gate. Refused: the panel's own project, a slug in use, a target directory already on disk. A failure before the row changes puts everything back; after, the rename stands and the response carries `warning`.
- **Piers (project groups):** `project_groups` rows (`owner_id`, `name` unique per owner case-insensitively) and a nullable `projects.group_id`; one pier per project. Organization only — a pier never changes what a project runs, reaches or is routed as; keep it that way (no shared ENV, convoys or routing through a pier). A pier is its owner's and holds only that owner's projects (the project PATCH/POST refuses another owner's pier, admins included), so piers live in LiveState `groups` and travel in the owner's fleet store; an ungrouped project has no `group_id` on the wire. `/api/groups` (every role, own only, 404 for others') names, renames and removes piers (removing one leaves its projects ungrouped) and `POST /:id/deploy` enqueues every project at it except the panel's own. A Crew move takes the moved projects out of their piers (listed in the plan); removing a user removes their piers. "Pier" is UI language only — code and API say group.
- **Fleet (agents) — phases 1–4:** another Skeppa can report to this one, its projects and admin pages are run from here, and it can lean on this panel's GitHub App. The master has `nodes` rows (`021_nodes.sql`; only SHA-256 hashes of the one-time join code and of the agent key, `nodes/keys.js`), admin-only `/api/nodes` (create → code, rename, `/code`, `/unpair`, delete, `GET /:id/deployments/:dep`) and the public `POST /api/nodes/join` (code → key). `bun scripts/join.js <master url> <code>` on the agent writes `agent.key` (chmod 600, next to the config; `AGENT_KEY_FILE`) and `MASTER_URL` into the config file. With `MASTER_URL` set, the agent (`agent/uplink.js`) dials `<master>/agent` with `Authorization: Bearer skn_…` — the master never needs a way in — and one socket carries envelopes `{ ch: 'live' | 'rpc' | 'ctl' }`: `live` is lazy-storage turned around (the agent serves a hub with only `uplink` — every project, pier, proxy and system record, fed by the bridge with `createLiveStores({ uplink: true })`, never openable by a browser — and `deploy-<id>`; the master is the client, `nodes/links.js`, and mirrors them into `node-<id>` / `node-<id>-deploy-<dep>`, admins only, served on `/live` beside the panel's own stores); `rpc` is master → agent from the agent's `METHODS` list only (`deployment`, and `request`: the master's `ALL /api/nodes/:id/api/*` relays an API call, which the agent runs through its own route modules (`createFleetApiApp` in app.js — projects, groups, deployments, github; every check theirs) as its first admin, only for `FLEET_PATHS` matched on the normalized path, answers ≤ 2 MB, a download as base64 that the master re-serves with its own attachment/nosniff/sandbox headers; the agent logs each change as `master: METHOD path`); `ctl` is the agent's hello (version) and the master's `watch` (someone looking → the agent's poller runs fast; the uplink session itself does not count). The upstream connection lives as long as the node, across reconnects, so deletions while offline arrive; an offline node keeps showing what it last reported. A key the master refuses is closed with 4401 and the agent backs off to minutes. LiveState `nodes` (in `panel`, `nodeInfo`) carries `online`; the web opens a `node-<id>` per `panel.nodes` and exposes `store.live.nodes` / `store.live.nodeStates` — never merged into `projects` (another database's ids). The node store also carries the agent's `images`. **The web side is one page for both:** `web/src/lib/ship.js` — the project page (`/projects/:id`, or `/fleet/:node/projects/:id` with `node`) provides a `ship` (`api` rewriting `/api/…` to the relay, `url` for links, `live` = that server's projects/groups/proxy/system/images, `home`, `link`), and everything under it injects it (`shipInject`, default this panel); `lib/vesselActions.js` takes it as a last argument. Code under the project page must read live state and call the API through the ship, never `store.live`/`api` directly. App.vue keys the router view by server and id on routes with `meta.project`. **Servers have pages, like projects:** the Fleet page (`/fleet`, admins) is a table a server a row — this panel first, then the fleet — with state, version, load, memory, disk and its vessel count (linking to the Harbor filtered by server), *Update panel* per server and *Update all*, adding a server (`JoinCode.vue`), and the Fleet log (`FleetLog.vue`); no project rows (they are the Harbor's). A server's own page, `/fleet/:node` (`ServerView`, `meta.nodePage`) — and this panel's, `/fleet/here` (the same tabs but Log and Pairing; the Fleet row *this panel* links there) — has tabs in `?tab=`: Overview (`ServerFacts.vue` — uptime, load against cores, memory and disk with meters, harbor gate; the same block that opens this panel's own Engine room — and its vessels as `ProjectRow`s with its ship), Engine room, Shipyard and Rigging — SystemView, ShipyardView and SettingsView embedded (`shipProvider`: the `node` and `embedded` props, `this.ship` provided below; embedded they leave the heading, the way back, `ShipOffline` and the Engine room's facts to the server page) — Log (`FleetLog` for that node) and Pairing (rename, a new join code, unpair, remove — kept apart). `ship.page('system'|'shipyard'|'settings')` on a node is that tab, and `/fleet/:node/system|shipyard|settings` redirect there; a node's project page leads back to the Harbor, its mooring form to the server's page. The Harbor has a server filter (`?server=here|<id>`, beside the search, once there is a fleet). A node's Rigging is its harbor gate and notifications only — Crew, GitHub App, Google sign-in and the account are hidden there (`FLEET_PATHS` covers system pm2/containers actions and logs, images, proxy, settings and the notify test; not users, not the GitHub App's own pages). **An agent's own panel is off:** with `MASTER_URL` set and no `AGENT_LOCAL_UI=true`, `createApp` (`hasLocalUi`) answers everything but `/api/webhooks` with a 404 naming the master, and index.js keeps `/live` shut; `AGENT_LOCAL_UI=true` brings the whole panel back, for when the master is gone. One master per trust zone: whoever controls the master controls its agents and reads their ENV. **GitHub through the master (phase 3):** the webhook route's push handling is `applyPush` (`github/push.js`), shared with the agent's rpc `push`; after verifying a push the master hands `pushSlice(payload)` (repo, ref, after, deleted, the head commit's first line and time — nothing else) to `links.forwardPush`, which calls every node whose reported projects deploy that repo (GitHub, no `git_url`), and keeps the latest per repo+ref for an offline one until it dials in (a node not heard from since the master started reports no projects and hears nothing). The fourth channel, `ask`/`answer`, runs agent → master: an agent whose own App is not configured uses `FleetGitHub` (`agent/github.js`, a `GitHubApp` that asks the master for `getInstallationToken`, `getRepoInstallation`, `listRepos`, `appOwnerLogin`; everything built on a token — clone, branch head, branches, repo root — is inherited and talks to GitHub itself), answered by `nodes/answers.js`: `githubToken` is `getScopedToken` — one repository, `contents: read`, cached — and only for a repo the node's reported projects deploy or one granted for 10 min because the admin asked about it through the relay (a branch list, suggestions, a project PATCH/POST naming it); an agent is never given an installation token. Its own App, once configured there, wins. **Mooring on a node:** `/fleet/:node/projects/new` is ProjectNewView with `shipProvider` (its repo list, suggestions and POST relayed; RepoPicker marks what that server moors); the project is owned by the admin the master acts as there, which the agent names in its hello (`adminId`, in LiveState `nodes`; 0 until it said), and the POST naming its repo grants that repo's token for the first deploy. **Shipyard across the fleet:** each server keeps its own definitions and engine store — nothing is shared; a Shipyard card's *Copy to…* (admins, with a fleet) puts the saved Containerfile onto picked servers through each one's ship (POST where the name is new, PATCH where it differs, nothing where it is the same) and optionally builds there. **A build is a store while it runs:** `build-<image id>` (`openBuild/appendBuild/closeBuild` in live/stores.js, the deploy-log shape, admins only; the store being open is what building means — a second one is 409), fed by `POST /api/images/:id/build` whether it streams (plain text, as ever) or answers `?detach=1` with a 202 at once; it closes after the row and LiveState have the result. An agent serves it to its master like a deploy log (`masterMayOpen`), mirrored as `node-<id>-build-<image>`. The Shipyard starts builds detached through the ship and follows the store (`subscribeLogs(id, fn, { node, kind: 'build' })`, which now ends with `{ type: 'end', code }` — `unknown-store` meaning nothing was running), here and on a fleet server alike, so long builds, reloads and other tabs all see it live; opening a card follows one under way or shows the last log (`GET /api/images/:id/log`), and Copy to… with a build follows each server's to its result. Never a bare `fetch` of the build route from the UI. **Away, and restarts:** a paired node not connected for 5 min (`offlineAlertMs`, from boot too) fires the `node_offline` notification once per absence, and again when it is back (`onNodeDown`/`onNodeUp`, index.js); an unpaired one is never missed. Each `node-<id>` store persists in `DATA_DIR/fleet-mirror.sqlite` (lazy-storage sqlite storage, `lease: false` — a cache rebuilt from the agent, not in the backups), so after a restart here the Fleet page and `forwardPush` have its last report before it dials in; the first sync after that deletes the projects and piers it no longer has (`reconcile`), and removing the node drops its rows. On its pages a node that is not reporting gets `ShipOffline` (`ship.online`, unknown counting as online), its project page falls back to the voyages it last reported and turns off what would ask it anything, the mooring form waits, its Rigging loads when it is back, and `ship.api` refuses at once while it is known offline. **Versions and updates:** the system record carries `version`, the short commit this checkout runs (`checkoutVersion`, computed once at boot — the poller is handed it), and an agent says its own in its hello; the Fleet page shows each server's against this panel's (green the same, amber `abc1234 ≠ def5678`, a count in the header). *Update panel* per server, and *Update all N panels*, deploy each server's own panel project through the relay — the pm2 project named its `system.selfPm2Name`, at the latest commit of the branch it follows; a server installed without one has none to offer, and one offline or mid-update is left out. **The harbor across the fleet:** an admin's Harbor list has a section per fleet server (paired, or with something reported; A–Z) under its own heading, with its piers and vessels at none — `ProjectRow` and `PierHead` take a `ship` prop, so a row's button, ⋮ and link run on that server — and `This server` over this panel's own when there is a fleet; the summary counts, the search and the state filter take them in, and the ship's log merges their voyages, tagged with the server's name and linked to its pages (`logEntries(lives, ownerOf, { link, keyPrefix })`). Pier folds are remembered by key — a pier id here, `<node>:<pier id>` for a fleet server's — as strings. The map draws a harbor per server — `HarborMap` takes `ship` (its ships' state, links, card and pier moves are that server's) and `legend` (only the last map carries it; its counts are the whole fleet's) — this panel's first under *This server*, each fleet server's under its name, unfiltered and dimmed by the search. *Deploy N with new commits* in the Harbor head deploys every vessel that is ahead, here and on every online fleet server, after one confirmation, saying what failed once — never a panel's own project (that is the Fleet page's Update). In the smoke suite, `seedStore` includes the fleet; tests about this panel's own harbor turn it off (`SEED.fleet = false` / `withoutFleet()`). **The Fleet log:** `fleet_events` (022, `nodes/events.js`) records, on the master, every change relayed to a node — `METHOD /api/path`, who (the signed-in admin), the subject as the node reported it then (`subjectOf`: the project, pier or image the path names, so a scuttle still says what), the status the agent answered and why it failed — and each node's life: created, paired (by its join code), renamed, new join code, unpaired, removed, offline, back. Reads are not logged; rows keep `node_name` and outlive their node; pruned to the newest 5000. `GET /api/nodes/events?node=&before=&limit=` (admins) feeds the Fleet page's log, in words via `web/src/lib/fleetLog.js`, refreshed after the page's own actions and every 20 s while visible. **One webhook for the fleet:** every notification goes through `sendEvent` in index.js; an agent with no webhook of its own asks its master (`ask` `notify`, nodes/answers.js), which sends it through its own webhook as `<node name>: <text>`, by the master's per-event settings, at most `NOTIFY_BURST` (30) per node in 10 min, only known events and http(s) links. A node's Rigging and the master's say so. **Disks:** each panel watches its own (`lib/diskwatch.js`, once a minute off `system.disk`): the `disk_full` notification at 90 %, once, and again when back under 85 % — an agent's through its master like the rest; the Fleet page shows each server's disk, a chip from 80 % (red from 90 %). **Shelved** (designed, not built — only with a real need): tenants on agents (a master tenant granted a node gets a password-less shadow user there; the relay carries who asks from the master's session and the agent runs the call as that tenant under its own tenant rules; per-owner node stores; GitHub tokens only from the tenant's own installation), and moving a project between servers (Rigging, the Manifest re-encrypted with the target's key, missing image definitions, and `shared/` streamed through the master in chunks — source stopped for the copy, target staged and deployed, the source restarted on failure and kept stopped as a fallback on success; the new address and DNS are the user's).
- **Subdomain routing ("harbor gate"):** a panel-owned Caddy instance (pm2 process `skeppa-proxy`, plain HTTP) routes `subdomain.<base_domain>` → `localhost:<project port>`; the admin's system Caddy forwards the wildcard to it with one static block and owns TLS. Config is generated as JSON (`server/src/proxy/`), hot-reloaded via the local admin API (never `:2019` — that's the system instance), cold-started via pm2. The routed port is injected into the app's env as `PORT`. A `static`-runtime project gets a file-server route instead (optional `try_files {path} /index.html` rewrite when `spa_fallback` → encode → `Cache-Control: no-cache` for HTML, `immutable` for hashed assets → `file_server`), rooted at its published snapshot — never at `source/`; a `gate_files` app gets those same file routes in front of its `reverse_proxy`.

## Commands

- `bun install` — install everything (workspaces)
- `bun run dev:server` / `bun run dev:web` — dev servers (Vite proxies `/api` and `/live` to :3000)
- `/harbor-lab.html?s=mixed|voyages|crowd|tenant` on the `dev:web` server — the harbor map on seeded scenarios, no backend or sign-in (`web/src/dev/harborLab.js`): a bar to moor, scuttle, set sail, land or fail, and a meter of fps and main-thread idle. Dev only; Vite builds just `index.html`. Whatever moves all the time on the map goes through the swell in `HarborMap.vue` (SVG attributes, 15/s) — never SMIL or an endless CSS animation inside the SVG, which have Chrome record the whole SVG again every frame; the lighthouse's beam is an HTML layer over the map, turned by the compositor (a click on the lighthouse puts it out)
- `/engine-lab.html` on the `dev:web` server — the Engine room on a seeded store (`web/src/dev/engineLab.js`): pm2 processes and containers in every state worth seeing (panel, harbor gate, external, stopped, an orphaned slug, a container near its memory limit). No backend, so logs and actions answer with errors. Dev only, like the harbor lab. The process tables fold columns away by zero width, never `display: none` — the logs row spans all nine
- `bun test` — server unit tests (in `server/test/`; bunfig.toml scopes the Bun runner there, so it never picks up the Vitest files)
- `bun run test:web` — frontend smoke tests (Vitest + @vue/test-utils under happy-dom, in `web/test/`): every view mounted for both roles against a seeded store, failing on any Vue render warning — the bug class where a template references something the instance never exposed
- `bun run build` — build the frontend to `web/dist` (served by Hono in prod)
- `bun scripts/install.js` — interactive server install (key file, dirs, .env, admin user, pm2 + safe `pm2 save`)
- `bun scripts/seed.js <user> <password>` — create/reset the admin user
- `bun scripts/join.js <master url> <code>` — pair this server as a Fleet agent of another panel (code from its Fleet page), then restart the panel; its own UI is off from then on unless `AGENT_LOCAL_UI=true`
- `bun scripts/backup.js [dir] [--keep N]` — snapshot `skeppa.db` via `VACUUM INTO` (default `DATA_DIR/backups`, keep 14). The master key is never included — back it up separately.
- `bun start` — run the server (serves `web/dist` if present)

## Directory layout

- `server/src/` — Hono app: `routes/`, `deploy/` (runner, git, pm2), `live/` (LiveState, the stores bridge, transport, poller), `github/`, `auth/`, `db/`, `lib/`, `proxy/` (harbor gate Caddy config + lifecycle)

## Security requirements (non-negotiable)

1. Webhook signatures (`x-hub-signature-256`) are verified with a timing-safe comparison against the **raw** body before any processing.
2. ENV values are encrypted at rest; the API returns them masked unless `?reveal=1` with a valid session.
3. Installation tokens and `MASTER_KEY` are never logged; git URLs containing tokens are redacted (`deploy/git.js`) and never persisted to `.git/config`.
4. Session cookies: `httpOnly`, `sameSite=lax`, `secure` in prod. WS upgrades validate the same session before upgrading.
5. The panel runs as its own non-root user; pm2 under the same user.
6. Any input that reaches shell commands or paths and is *not* the intentional deploy script (slugs, branch names, pm2 names, cwd, publish dir, env keys) is whitelist-validated in `lib/validate.js`. A valid pm2 name is still not permission to act on that process: see "Configured vs deployed runtime". Processes are spawned with args arrays — no shell interpolation of user data. The deploy script itself intentionally runs as shell; the UI says so.
7. Browsers have one WebSocket, lazy-storage's at `/live` (the other, `/agent`, takes only a Fleet agent's key — never a session — and the agent answers it only from its `uplink`/`deploy-<id>` stores and its `METHODS` list — `request` only for `FLEET_PATHS`; what an agent asks back is answered only from `nodes/answers.js`, never with more than a one-repo read token); its protocol is the library's, and a client may open only the stores `authorize` allows (`live/stores.js` `canOpen`: fleets by ownership, `panel` admins only, `deploy-<id>` via `canReadDeployment` wired in index.js — deploy logs echo ENV values). Sockets carry the user from the upgrade's session cookie, and every store is read-only for clients (`readOnly: true`).
8. Anything the panel spawns (deploy scripts, pm2, git) gets a minimal sanitized environment — the panel's own `process.env` (MASTER_KEY!) must never be inherited by child processes; pm2 injects its CLI env into the apps it starts, so this applies doubly there.
9. The file viewer serves only regular files whose *real* path is inside the project's `source/` (never `.git`, never the panel-written `.env`), downloads always as `attachment` + `application/octet-stream` + `nosniff` + `CSP: sandbox` so repo content never renders on the panel's origin, and anything rendered from a file into `v-html` goes through the escape-first renderers — never a raw string, never a sanitizer-less Markdown library.
